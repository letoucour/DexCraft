# DexCraft — mémoire du projet

Ce fichier remplace l’historique des conversations. Toute session Claude Code doit le lire en premier (avec `CLAUDE.local.md`, notes privées non publiées), puis `index.html`.

## 1. Le projet en deux phrases

DexCraft est un jeu de collection de cartes Pokémon en français, inspiré de wiki-masters.com : on ouvre des boosters, on complète une collection et on échange entre joueurs (les enchères ont été retirées en 0.5.0). Sorti de bêta avec la 1.0.0 (version affichée en bas à gauche), sans limite de joueurs.

**Propriétaire du projet :** Theo (theo.lostria@gmail.com), administrateur du jeu.

## 2. Architecture

- **`index.html`** : tout le jeu, environ 4 900 lignes (500 Ko), souvent très longues (les données `DEX` et `EVO` tiennent chacune sur une seule ligne). HTML, CSS et JavaScript dans un seul fichier, sans dépendance à part `supabase-js` chargé depuis un CDN.
- **Hébergement (0.8.8)** : **https://dexcraft.fr**, domaine acheté chez OVH (renouvellement automatique), DNS gérés par Cloudflare (serveurs `denver` et `june.ns.cloudflare.com` ; e-mails : Cloudflare Email Routing, contact@dexcraft.fr renvoyé vers la boîte Gmail de Theo (réception seulement ; les MX OVH ont été supprimés, la boîte Zimbra d’OVH n’est pas active) ; DNSSEC actif depuis le 28/09/2026 : signé par Cloudflare (clé 2371, algorithme 13), enregistrement DS déclaré chez OVH, onglet « Enregistrements DS » ; l'interrupteur DNSSEC d'OVH reste désactivé. Pour l'arrêter un jour : retirer d'abord le DS chez OVH, attendre 24 h, puis désactiver chez Cloudflare, sinon le site devient injoignable). Site publié par **Cloudflare Pages** (projet `dexcraft`, relié au dépôt GitHub, branche `main` : chaque push redéploie). Commande de publication : `mkdir -p dist && cp -r index.html images favicon.svg favicon-32.png apple-touch-icon.png _headers dist/`, dossier publié `dist` : seuls ces fichiers sont en ligne (pas les scripts SQL, outils, notes). **Un nouveau fichier à mettre en ligne doit être ajouté à cette commande** (Cloudflare, Workers & Pages, dexcraft, Settings, Build). `www.dexcraft.fr` redirige vers `dexcraft.fr` (règle de redirection Cloudflare). L'ancienne adresse `letoucour.github.io/DexCraft` (GitHub Pages, toujours active tant que le dépôt est public) et `dexcraft.pages.dev` renvoient vers dexcraft.fr par un script en tête de page. Supabase, Authentication, URL Configuration : Site URL `https://dexcraft.fr`, Redirect URLs `https://dexcraft.fr/**`, `https://dexcraft.pages.dev/**` (et l'ancienne adresse). Vérifier un déploiement : `curl -s https://dexcraft.fr/ | grep APP_VERSION`.
- **Base de données** : Supabase (production `hxrbzhmzjeuhmaioqhdd`, test `thgyzfjozfhwefrztjfh`). Comptes e-mail et mot de passe. Table `docs` (`path`, `coll`, `data` jsonb, `updated_at`), table `admins`, table `game_config` (données du jeu pour le serveur), table `vb_rounds` (plateaux cachés de la VoltoBataille).
- **Scripts SQL, dans l'ordre** : `dexcraft-supabase.sql` (tables et droits) ; configuration en **deux fichiers** (l'éditeur SQL de Supabase tronque au-delà de ~40 000 caractères) : `dexcraft-config.sql` PUIS aussitôt `dexcraft-config-2.sql` et `dexcraft-config-3.sql` (données de l'Arène depuis la 1.3.0 : `arena`, `arStat`, `arChart`, `arBase`, clés `P3` de l'export) (évolutions `evo`, réserves de tirage `pool`, titres `titleDefs`… ajoutés à la partie 1 ; sans elle, évolutions et titres ne marchent plus), générés par `outils/generer-config.ps1` depuis `index.html?export-config` (clés de la partie 2 : liste `P2` de l'export) : à régénérer et relancer après tout changement de cartes, raretés, titres, boutique ou VoltoBataille ; puis `dexcraft-serveur.sql`, `dexcraft-serveur-2.sql`, `dexcraft-serveur-3.sql`, `dexcraft-serveur-4.sql`, `dexcraft-serveur-5.sql` (fonctions du jeu en cinq parties depuis la 1.3.0, la 5e pour l'Arène ; **chacune sous 40 000 caractères** : les compter avant de livrer ; chaque partie révoque elle-même les droits de ses fonctions) ; puis `secret/cartes-secretes.sql` (cartes secrètes, généré par `generer-config.ps1` sur le PC de Theo, jamais publié). **`migrations/`** : scripts passés une fois, par version. Ne jamais relancer `migration-1.0.0.sql` ; relançables sans risque (recalcul de tous les profils) : 0.8.9, 1.1.0, 1.1.7, 1.1.8, 1.1.14, 1.2.0 (qui corrige aussi la rareté des annonces). Une nouvelle migration va dans ce dossier.
- **Chemins de données** : `players/<uuid>` pour un profil, `market/<id>` pour une annonce.
- **Le serveur est l'arbitre (depuis la 0.4.0)** : les joueurs ne peuvent QUE LIRE `docs`. Toute modification passe par une fonction SQL `dc_*` (`security definer`), appelée via `rpc(name, args)` dans `index.html`, qui renvoie le profil à jour. Hasard tiré côté serveur (`dc__rnd`, `gen_random_bytes`). Champs calculés par `dc__stamp` : `unique`, `byr`, `total`, `myth`, `trans`, `masterTs`, `beta`, `stats.maxCr`, `stats.days`. Les fonctions `dc__*` sont internes (non exécutables par les joueurs). Pour une nouvelle action : écrire une fonction `dc_*` qui vérifie tout, la tester sur PostgreSQL local, jamais d'écriture directe depuis le navigateur.
- **Tests** : sur ce PC (`localhost`, `127.0.0.1` ou fichier ouvert), `index.html` se branche automatiquement sur le projet Supabase de **test** (« BASE DE TEST » en bas à gauche). `outils/serveur-local.ps1` sert le jeu sur http://localhost:8123 et http://127.0.0.1:8123 (deux sessions, deux comptes). Comptes de test : `theo.lostria+test1@gmail.com` (admin) et `+test2`. PostgreSQL 17 est installé sur le PC pour tester le SQL hors ligne.
- **Codes cadeaux** (partie 3) : table `promo_codes` (`code` en majuscules, `credits`, `packs`, `active`, `max_uses` total ou null, et depuis la 1.2.6 `spec` : boosters spéciaux rangés dans l'inventaire, par exemple `'{"prem": 1}'` ou `'{"gen:3": 2, "type:10": 5}'`) et `promo_redemptions` (un code une fois par joueur). Section « Entrer un code » en bas du profil, fonction `dc_redeem_code`. Au plus 10 codes inconnus par heure et par joueur (`promo_tries`, 0.8.7 ; un code inconnu renvoie `{error}` au lieu d'une exception, pour que l'essai soit compté). Créer un code : `insert into public.promo_codes (code, credits, packs) values ('NOEL', 500, 5);` **dans l'éditeur SQL seulement, jamais dans un fichier du dépôt** (dépôt public). Désactiver : `update public.promo_codes set active = false where code = 'NOEL';`. Liste des codes existants : `CLAUDE.local.md` (privé).
- **Suppression d'un compte** (partie 3) : supprimer un utilisateur dans Supabase (Authentication, Users) supprime aussi son profil, sa manche de VoltoBataille et ses annonces (déclencheur `dc_user_deleted` sur `auth.users`, fonction `dc__purge_player`) : enchérisseurs remboursés, propositions rendues.
- **Couche de lecture (0.6.0, allégée en 0.8.4 pour le trafic de l'offre gratuite de Supabase, 5 Go par mois)** : on ne télécharge jamais les collections de tout le monde, seulement ce qui a changé, et rien quand l'onglet est caché (`document.hidden` ; au retour après plus de 30 s, tout est relu, `visibilitychange`). `loadPlayers` lit un résumé par joueur (`PL_FIELDS` : pseudo, image, titres affichés `shown`, compteurs du classement), chaque minute sur l'onglet Classement, toutes les 5 minutes ailleurs (`pollShared`). Son propre profil : temps réel filtré sur sa ligne (`dc-me`) ; chaque minute, `loadMe` lit seulement `data->updated` et ne relit le profil entier que s'il a changé (`onMine`, ignoré pendant une action `rpcBusy`). Marché : temps réel (`dc-market`) ; toutes les 2 minutes, `loadMarket` lit la liste légère (`path`, `updated_at`) puis seulement les annonces nouvelles ou modifiées (`MARKET_TS`) : toute modification d'une annonce côté serveur doit donc mettre à jour `updated_at`. Lectures longues paginées par 1 000 (`selectAll` : Supabase ne renvoie jamais plus de 1 000 lignes d'un coup). Collections des seuls auteurs d'annonces d'échange (`loadOwnerColls`, `OWNER_COLL`) : nouveaux auteurs tout de suite, toutes relues au plus toutes les 5 minutes. Profil complet d'un autre joueur seulement quand on l'ouvre (`loadPlayer`). Les titres affichés des autres joueurs viennent de `shown`, calculé par `dc__stamp` à partir de `cfg.titleDefs` (exporté par `titleDef` : un nouveau genre de titre doit être ajouté dans `titleDef` ET dans `dc__stamp`). Plus de partie locale : sans connexion, seul l'écran de connexion s'affiche.
- **Avertissements de Supabase (Security Advisor)** : « Signed-In Users Can Execute SECURITY DEFINER Function » est voulu (les `dc_*` sont l'interface du jeu ; chaque `dc_admin_*` vérifie l'administrateur). « Function Search Path Mutable » : corrigé en 0.8.4 par un bloc à la fin de chaque partie serveur, qui fixe `search_path = public, extensions` sur toute fonction `dc_*` qui n'en a pas. « Leaked Password Protection » : réservé à l'offre Pro.
- **Historique des échanges** (partie 3) : table `trade_log`, écrite par `dc_trade_answer`, lisible seulement par les deux joueurs concernés (RLS). Bouton « Voir l'historique de mes échanges » dans l'onglet Échanges.
- **Récompense quotidienne** (partie 3) : `dc_daily_claim`, une fois par jour (heure de Paris), série de 7 jours `DAILY` dans `index.html` (exportée dans la config), qui repart à 1 si un jour est manqué. Depuis la 1.0.3 : progression exponentielle (×1,47 par jour), boosters 1, 1, 2, 3, 5, 7, 10 et crédits 300, 450, 650, 950, 1 400, 2 000, 3 000 (pas de rattrapage des séries en cours : choix de Theo). Profil : `daily = {day, streak}`. Encadré « Récompense du jour » sur l'écran des boosters.
- **Mot de passe oublié** : lien sur l'écran de connexion (`resetPasswordForEmail`, retour sur la page avec `type=recovery`, formulaire `#gate-reset`, `updateUser`). Supabase, Authentication, URL Configuration : l'adresse du site doit être dans Site URL ou Redirect URLs.

## 3. Règles du jeu, à ne pas casser

### Raretés, dans l'ordre des indices 0 à 7

| Indice | Rareté | Taux par carte | Défausse |
|---|---|---|---|
| 0 | Commune | 43,2634 % (le reste ; 53,2634 % de la 1.1.8 à la 1.2.0) | 2 |
| 1 | Peu commune | 30,6 % (26,6 % avant la 1.2.0) | 5 |
| 2 | Rare | 15,7 % (11,7 % avant) | 10 |
| 3 | Épique | 6,9 % (4,9 % avant) | 15 |
| 4 | Mégas & Gigamax (méga-évolutions et Gigamax) | 2 % | 18 |
| 5 | Légendaire | 1,5 % depuis la 1.1.8 (1 % avant) | 20 |
| 6 | Mythique | 1 sur 4 096 | 50 |
| 7 | Transcendante | 1 sur 8 192 | 100 |

- Le tirage se fait sur `SCALE = 8 192 000` pour que 1/4096 et 1/8192 tombent juste. Le total doit toujours faire exactement `SCALE`.
- **Réserves de tirage (1.1.8)** : le tirage choisit la rareté, puis une carte dans `POOLS[r]` (exporté en `cfg.pool` pour les raretés 4 et 5, lu par `dc_open`, sinon `byr`). Les 14 Méga et Gigamax de légendaires et fabuleux (`LEG_SPECIAL` : Méga-Mewtwo X et Y, Latias, Latios, Rayquaza, Heatran, Darkrai, Zygarde, Diancie, Magearna, Zeraora ; Melmetal et Shifours ×2 Gigamax) restent en rareté 4 (compteurs, titres, défausse, échanges) mais sont tirées dans la réserve des Légendaires ; intitulé « Légendaire Méga-évolué » ou « Légendaire Gigamax » (`rarName`) et scène Légendaire (`fxRar`). Choix de Theo : avant, une Méga-Rayquaza sortait plus souvent que Rayquaza.
- **Rééquilibrage de la 1.2.0 (choix de Theo)** : 10 points retirés aux Communes, +4 aux Peu communes, +4 aux Rares, +2 aux Épiques ; et 30 Peu communes passées Communes (Pokémon de base, jamais issus d'une évolution : Posipi, Pachirisu, Emolga…) et 30 Rares passées Épiques (fins d'évolution : les 8 évolutions d'Évoli, Lucario, Gardevoir, Alakazam…), liste `RAR_FIX` juste après `DEX` (les formes suivent). Chance par carte ensuite strictement décroissante : 0,116 %, 0,092 %, 0,069 %, 0,050 % (avant, une Épique sortait aussi souvent qu'une Rare). Annonces et profils corrigés par `migrations/migration-1.2.0.sql`.
- Les 2 % des Mégas ont été pris sur les quatre premières raretés : 1,2 point aux Communes, 0,4 aux Peu communes, 0,3 aux Rares, 0,1 aux Épiques.
- **Ajouter une carte mythique ou transcendante ne change jamais le taux global de sa rareté**, seulement la répartition à l'intérieur.
- Le tirage de la carte (rareté et Pokémon) ne dépend jamais de la collection du joueur. Seule exception, voulue par Theo (1.1.0) : la chance qu'une carte déjà tirée sorte en shiny dépend du nombre de fois où le joueur l'a obtenue (voir « Shiny »). `rnd()` élimine le biais de modulo par rejet.

### Shiny (1.1.0)

- **Taux** : à chaque carte tirée dans un booster (`dc_open`, seulement là), (1 + `got[carte]`) chances sur 4 096 (`SHINY_BASE`), sans plafond depuis la 1.1.11 (`SHINY_MAX = SHINY_BASE` ; 100 sur 4 096 au plus avant, retiré à la demande de Theo : on doit pouvoir chasser un shiny précis). `got` = nombre de fois où le joueur a obtenu la carte (booster, évolution, échange conclu, boîte cadeau), compteur qui ne baisse jamais : fonction `dc__gain` (partie 1) = `dc__add` + `got`. Une carte **rendue** (proposition refusée, annonce retirée) passe par `dc__add` seul et n'est pas comptée. Au lancement, `migration-1.1.0.sql` a rempli `got` avec les exemplaires possédés (relançable : garde le plus grand).
- **Une fois par carte** : le shiny est une version débloquée pour toujours (`shiny = {id: date}` dans le profil), jamais échangée, défaussée ni consommée ; la carte tirée est ajoutée normalement à la collection. Un Pokémon jamais obtenu peut sortir directement en shiny (1/4096).
- **Jamais de shiny** : mythiques, transcendantes, et les cartes sans illustration shiny (`SHINY_NONE` dans `index.html`, exporté en `cfg.shinyNo` ; vide au lancement). Illustrations : `images/shiny/<n°>.webp` (les 1 324 cartes du Pokédex, sauf Terapagos Stellaire ; Zarbi A 201, Méga-Carchacrok Z 4056 et Méga-Nigirigon 4092 fournies par Theo, converties comme les images perso), téléchargées par `outils/telecharger-shiny.ps1` (PNG dans `images-shiny-png/`, ignoré par git ; manquantes dans `outils/shiny-manquantes.csv`). Une image ajoutée à la main : la placer dans `images/shiny/`, retirer son numéro de `SHINY_NONE`, régénérer la configuration.
- **Affichage** : la forme shiny remplace la normale partout où le joueur voit ses propres cartes (collection, fiche, révélé, image de profil, partage) ; bascule par carte dans la fiche (`shinyOff`) et réglage « Toujours afficher les formes normales » dans le profil (`shinyNorm`), tous deux par `dc_shiny_view` (partie 3), donc identiques sur tous les appareils. Image de profil en shiny visible par tous (`avaS`, calculé par `dc__stamp`, lu par `PL_FIELDS`). Depuis la 1.2.0, la forme se choisit avec l'image : un Pokémon débloqué en shiny apparaît deux fois dans la recherche du profil, normal et ✨ (`dc_set_avatar(p_id, p_shiny)`, champ `avaSh` ; historique `avaHist` : un numéro, ou `{i, s: 1}` pour une image shiny) ; sans `avaSh` (image choisie avant), l'ancienne règle (forme affichée dans la collection).
- **Révélé** : rien ne trahit un shiny avant le retournement ; ensuite étiquette « ✨ Shiny ! » et pluie d'étoiles (`shinyFx`, éphémère), « Légendaire shiny ! » dans la scène Légendaire. `dc_open` renvoie `shiny: true` sur la carte (aussi dans `lastOpen`).
- **Classement** : ordre inchangé ; la barre se couvre d'une aura holographique (`lb-aura`, statique) proportionnelle à `shinyN` / cartes qui existent en shiny. `shinyN` (et `stats.shinyN` pour les titres) calculé par `dc__stamp`. Profil et fiche d'un joueur : « ✨ N shiny ». Titres (groupe Shiny, noms choisis par Theo) : Première étoile (1), Daltonien (10), Shiny Hunter (50), Légende Chromatique (200), « Dormir n’est pas une option » (tous, `shinyAll`, `need = shinyTotal()`).
- **Message aux joueurs (voulu par Theo)** : garder ses cartes n'augmente pas la chance, un exemplaire obtenu compte pour toujours même échangé, défaussé ou utilisé pour une évolution (règles de l’écran des boosters ; depuis la 1.1.11, l’encadré Shiny de la fiche dit seulement « Vous avez eu cette carte un total de N fois, ce qui porte votre chance… à X/4 096, soit Y %. », à la demande de Theo).
- **Fiche d'une carte** : « obtenue N fois au total », chance shiny au prochain tirage, ou date d'obtention du shiny et bascule. Collection : filtre « Shiny ✨ », tri « fois obtenue ».

### Économie et rythme

- Nouveau joueur : 1 900 crédits, 10 boosters (depuis la 1.0.0 ; 3 100 crédits avant). Pack gratuit « Lancement de DexCraft » (1.0.0) : 1 000 crédits et 10 boosters, une fois par joueur, dans la boutique (`LAUNCH`, exporté dans `cfg.once`, récupéré par `dc_buy_once`, clé `lancement` dans `bought`) ; pour arrêter l'offre, `LAUNCH = null` et régénérer la configuration. **Durée limitée depuis la 1.2.0 : jusqu'au 14 octobre 2026 inclus**, heure de Paris (`LAUNCH.until`, exporté dans `cfg.once`, refusé ensuite par `dc_buy_once` : « Cette offre est terminée. » ; `launchOn` cache l'offre et l'annonce une fois la date passée). Annonce « 🎉 DexCraft est officiellement lancé ! » sous le titre de l'écran des boosters (`launchNewsHTML`, 1.0.4), avec un lien vers la boutique, tant que le joueur n'a pas récupéré le pack ; ensuite « ✨ Personnalisez votre profil et votre environnement de jeu, et gérez vos titres, en cliquant sur votre pseudo » (lien vers le profil ; disparaît une fois cliqué, `dc-look-news` gardé sur l'appareil, 1.0.5).
- **Boosters spéciaux (1.2.3, idée de Theo : que faire des crédits en dehors des boosters)** : payés en crédits par 1, 5 ou 10 (`SPB`, `buySpecial`, `dc_buy_special`) et, depuis la 1.2.5 (demande de Theo), rangés dans un **inventaire** (`spInv = {"prem": n, "gen:3": n, "type:10": n}` dans le profil) : encadré « 🎒 Mes boosters spéciaux » sous la réserve de l'écran des boosters (`spInvHTML`), un clic sur un sachet le met **à la place du booster de base** au centre (`spActive`, `spActiveNow` : sachet aux couleurs du booster, boutons Ouvrir, 5, 10, ligne « N en stock · Revenir au booster normal ») ; le stock épuisé, le booster de base revient, et sa réserve gratuite continue de se remplir pendant ce temps (`openSpecial`, `dc_open_special` qui consomme l'inventaire, 10 au plus d'un coup), liste aussi dans « Mes boosters » (compteur de l'en-tête) ; avant, ils s'ouvraient à l'achat (`SPB`, section `#shop-special` de la boutique (entre la première rangée, qui garde Boosters, Badge Soutien et le pack événement, et les packs cosmétiques ; rubriques annoncées en haut par « Plus bas : » `.shop-nav`, `shopGo`), bouton « ✨ Boosters spéciaux » sur l'écran des boosters, `goto-special` ; en fin d'ouverture, « Booster suivant » tant qu'il en reste en stock, `lastSpecial`). **Génération** (300 crédits depuis la 1.2.4, 500 avant, 5 cartes de la génération choisie, `genOf`) et **Type** (300, 500 avant, 5 cartes du type choisi) : même tirage de rareté qu'un booster normal, seule la liste des Pokémon change, jamais de mythique ni de transcendante (le booster doit toujours respecter ce qui a été acheté, demande de Theo) ; une rareté sans aucune carte du choix serait retirée du tirage (aucune aujourd'hui ; le plus juste : Insecte Légendaire, 1 carte). **Premium** (750 crédits depuis la 1.2.4, 2 000 avant ; 5 cartes Rare ou mieux, `PREM_K` exporté en `cfg.premK`) : chances d'un booster normal réparties sur les seules raretés Rare et plus, mythiques et transcendantes comprises (choix de Theo, 1.2.4 : Rare 60,07 %, Épique 26,40 %, Méga 7,65 %, Légendaire 5,74 %, mythique 1/1 070, transcendante 1/2 141 par carte). À 750, autant de cartes Rare ou mieux que 3,8 boosters normaux (765 crédits) : jeu égal sur les cartes fortes, les boosters normaux gardent les Communes, la défausse et plus de tirages shiny ; à 500, il aurait été 53 % plus rentable (écarté par Theo). Serveur : partie 4 (`dc__open_special`, `dc__sp_key`, `dc_buy_special`, `dc_open_special`, `dc_admin_give_booster`) ; génération et types de chaque carte dans `cfg.spCard` (3 caractères par carte de `dexOrder`). Comptent comme boosters ouverts (titres, Chanceux), shiny comme un booster normal, 50 dernières cartes. Mode développeur : gratuits, et « Booster à offrir » (toutes les sortes, boîte cadeau ; entrée `{sp, v, n}` : les spéciaux vont dans l'inventaire à l'ouverture du cadeau, `dc_gift_open` renvoie `spec`).
- Un booster gratuit toutes les 10 minutes, réserve de 10 maximum. Les boosters achetés vont dans une réserve séparée (`bonus`), sans limite, et sont consommés après les gratuits.
- Ouverture par 1, 5 ou 10 boosters maximum (`OPEN_OPTS`). Les ouvertures par 20, 50 et 100 ont été retirées.
- Pseudo : jamais tiré de l’e-mail. Un nouveau compte reçoit « Dresseur 1234 » et doit choisir son pseudo à la première connexion (`pseudoSet`, fenêtre `pseudoFirstDlg` qu’on ne peut pas fermer). Règles serveur (`dc__pseudo_check`) : 3 à 20 caractères (lettres, chiffres, espaces, . _ -), unique sans tenir compte des majuscules, accents et signes (`dc__pseudo_key`), liste de mots interdits, noms réservés (TheoToucour, DexCraft, admin, modo…) sauf pour l’administrateur. Ensuite un changement tous les 7 jours (`pseudoTs`), après une boîte de confirmation. L’outil administrateur n’est pas soumis au délai ; un pseudo effacé par l’administrateur redemande un choix au joueur.

Les anciennes offres en euros (packs de crédits, Pack fondateur, Démarrage, Wailord) sont retirées, côté jeu et côté serveur (`creditPacks` vide dans la configuration ; `once` ne contient plus que le pack gratuit de lancement). L'encadré vert « DexCraft se joue entièrement gratuitement » est à garder.

Titre `lord` : condition `{c:"cos",i:"titre.lord"}` (dans `titleDef` et `dc__stamp`).

L221-28 13°) → fonction Supabase `dc-paiement` (`supabase/functions/`, crée la session Stripe Checkout, note `payments` en « pending ») → page Stripe (carte ou PayPal) → Stripe appelle `dc-stripe-webhook` (signature vérifiée) → `dc_pay_grant` (réservée au rôle service, idempotente, vérifie le montant) livre le pack. ### Marché

- **Échanges** : le proposant met sa carte de côté, et c'est le propriétaire de l'annonce qui accepte ou refuse. Quatre types de demande : n'importe quelle carte de la rareté, n'importe laquelle **qui lui manque** (valeur par défaut), un Pokémon précis (`want`), ou **une liste de cartes précises** (1.0.3, `wantList` : 2 à 50 cartes du Pokédex de même rareté ; `dc__want_list` les filtre, une liste d'une seule carte devient `want`). Liste choisie dans le sélecteur `wantPickOpen` (recherche, « Seulement celles qui me manquent », bouton « 🔔 Ajouter mes cartes recherchées », silhouettes pour les cartes pas encore obtenues), depuis la fiche d'une carte (« Plusieurs cartes précises… »), la mise à l'échange groupée (`p_wants` de `dc_trade_create_many` : chaque annonce garde les cartes de sa rareté, celles sans aucune ne sont pas publiées, `nolist`) et « Mes annonces » (« Demander : une liste de cartes… », `dc_trade_bulk` mode `list`, annonces sans carte de leur rareté inchangées). `dc_trade_propose` refuse une carte hors de la liste ; côté page `canOffer` et `tradeWants`.
- **Dresseur d'origine (1.1.13, idée de Theo, contre les allers-retours qui gonflaient la chance de shiny)** : chaque exemplaire garde le dresseur qui l'a obtenu (booster, évolution, cadeau), même après plusieurs échanges, et ce dresseur ne peut JAMAIS le récupérer (circuit à trois compris). Profil : `ot = {n°: {uid: nombre}}` = exemplaires venus d'autres dresseurs, le reste est au nom du joueur (toutes les cartes d'avant la 1.1.13, sans migration). Annonce et proposition : champ `ot` de la carte mise en jeu ; on met en jeu d'abord un exemplaire à son nom (`dc__ot_take`, partie 2, qui évite aussi le destinataire connu) ; réception ou retour avec son origine (`dc__ot_give`) ; `dc_trade_propose` refuse une annonce dont on est le dresseur d'origine ; `dc__stamp` ne garde jamais plus d'exemplaires étrangers que d'exemplaires possédés (défausse et évolution consomment d'abord ceux à son nom). Anciennes annonces sans `ot` : au nom de leur propriétaire. Page : `otFrom`, `canOffer`, ligne « DO » (abréviation des jeux Pokémon, infobulle « Dresseur d’origine », choix de Theo) de l’annonce et de la fiche d’une carte (`otLine`), étiquette « Vient de vous » sur les tuiles.
- **Enchères : retirées en 0.5.0**, onglet, fenêtre de mise en vente, titres et textes compris. Ne pas les réintroduire sans demande de Theo.
- **Règle d'or du marché** : tout se règle côté serveur, de façon atomique (verrous de lignes). `dc_trade_propose` met la carte de côté, `dc_trade_answer` échange les cartes et rend celles des autres propositions, `dc_trade_cancel` rend tout. Le profil n'a plus de `listings` ni d'`escrow` : les annonces se lisent sur le marché.

## 4. Interface, décisions prises

- Booster (0.6.3) : sachet holographique (maquette retenue parmi 4, `prototypes/boosters.html`) : bords en dents de scie, reflet qui passe en boucle, dans chaque morceau découpé (`.pk-skin::after`), inclinaison vers le pointeur (`--rx`, `--ry`). Ouverture (`.pack.tear`, ≈ 1 s) : le haut se déchire le long des pointillés, une lumière jaillit, le sachet tombe.
- Ouverture de booster : main de cartes en éventail, défilement horizontal, carte centrale mise en avant. **Performance mobile** : jusqu'à 50 cartes en main (10 boosters). Éventail (1.1.1) : pivot au centre de la carte, descente et rotation plafonnées (`fanUpdate`), pour que les cartes éloignées restent entières dans la marge du bas de la main (elles étaient coupées sur grand écran). La 3D n'est active que sur la carte en cours de retournement (classe `.flipping`, retirée après 650 ms) ; au repos, dos seul ou face à plat, jamais de `will-change`. Ne pas remettre de 3D ou d'animation permanente sur toutes les cartes de la main : sur téléphone, la mémoire graphique sature et la page se recharge. Pendant une ouverture (dès l'appel au serveur), `html.revealing` bloque le « tirer pour actualiser ». Sur téléphone (≤ 700 px), la main est un peu plus petite pour que les boutons restent au-dessus de la barre d'onglets. **Réponse perdue (0.8.3)** : `dc_open` garde le dernier tirage dans le profil (`lastOpen = {t, drawn}`) ; si l'appel échoue, `recoverOpen` relit le profil et, si le compteur `stats.packs` a avancé, montre ce tirage (un joueur sur mobile avait perdu l'affichage de 10 boosters). **Fin d'ouverture (1.1.15)** : boutons « Retour » (écran des boosters) et « Booster suivant » (ou « N boosters suivants », même nombre que la dernière ouverture si possible, sinon 1 ; `nextOpenK`, `lastOpenK`, action `next-pack`), absent s'il ne reste aucun booster ou après un cadeau. **Dernières cartes tirées (1.2.0)** : `dc_open` garde les 50 dernières cartes tirées (`recent`, les plus récentes d'abord) ; boîte discrète « 🕘 Dernières cartes tirées » sous « Comment ça marche ? », sans aucune illustration depuis la 1.2.2 (les vignettes se mettaient à jour avant la fin de l'ouverture et dévoilaient le tirage) (`recentHTML`, sous le booster sur téléphone), fenêtre `recentDlg` en petites cartes ; avant la première ouverture en 1.2.0, le dernier tirage (`lastOpen`). « Comment ça marche ? » est dans un encadré (`.rules-box`) depuis la 1.2.0. **Ouverture pas finie (1.1.1)** : le tirage et les cartes déjà retournées sont gardés sur l'appareil (`saveReveal`, localStorage `dc-reveal`) dès la réponse du serveur ; à la connexion suivante, `restoreReveal` reprend la main là où le joueur l'avait laissée (booster : seulement si c'est toujours `lastOpen.t` ; cadeau : moins d'un jour). Effacé dès que tout est retourné.

Gains versés en crédits dans la limite de `VB_CAP` = 3 000 par jour (2 000 avant la 1.3.0) (barre de progression, remise à zéro à minuit heure du joueur). Profil : `volto = {day, gained, level}`. ## 5. Contraintes permanentes

- **Tout en français**, y compris les messages d'erreur et les commentaires de code.
- **Ne jamais dévoiler** l'existence des mythiques et des transcendantes dans un texte visible par un joueur qui n'en possède pas.
- **Illustrations** : `IMG_URL = "images/{id}.webp"` (chemin relatif, jamais de `/` au début : le jeu marche à n'importe quelle adresse), WebP 256 × 256 qualité 80 (`magick <png> -resize 256x256 -quality 80`, ou pour une image fournie : `-trim +repage -resize 240x240 -background none -gravity center -extent 256x256`) ; shiny dans `images/shiny/`, fiche d'appli dans `images/app/`. Surtout les illustrations officielles de PokeAPI ; exceptions fournies par Theo ou tirées de Pokémon HOME (voir « Cartes » et « Shiny »). Mythiques et transcendantes : images fournies par Theo, noms impossibles à deviner. PNG d'origine dans `images-png/`, `images-shiny-png/` et `images-perso/`, ignorés par git. Les illustrations appartiennent à Nintendo, Game Freak et The Pokémon Company : risque de demande de retrait, choix assumé par Theo.
- **Anti-triche** : depuis la 0.4.0, le navigateur n'a plus aucun droit d'écriture. Ne jamais réintroduire d'écriture directe dans `docs` depuis `index.html`, ni de calcul de hasard ou de gains côté navigateur : tout passe par `dc_*`.
- **Le dépôt est public** : ne jamais y écrire un code cadeau, le nom d'une carte secrète ou une donnée privée. Notes privées : `CLAUDE.local.md` (ignoré par git, à lire aussi). Dossiers ignorés : `secret/` (cartes secrètes), `sauvegardes/` (copies de la base : e-mails des joueurs).
- **Sécurité (0.8.7)** :
  - `supabase-js` chargé avec son empreinte (`integrity`, SRI) : à recalculer si on change de version (commande en commentaire au-dessus de la balise).
  - Balise `Content-Security-Policy` dans `<head>` : scripts seulement depuis le site, jsDelivr et Cloudflare (Turnstile), données seulement vers Supabase. Toute nouvelle ressource externe doit y être ajoutée. `_headers` : les mêmes règles plus l'interdiction d'afficher le jeu dans un cadre, pour Cloudflare Pages (ignoré par GitHub Pages).
  - 1 000 annonces d’échange ouvertes au plus par joueur (`dc__listing_cap`, `dc__open_listings`, partie 2 ; `dc_trade_create_many` publie jusqu'au plafond et renvoie `capped`).
  - Anti-robots Cloudflare Turnstile sur inscription, connexion et mot de passe oublié : `TURNSTILE_SITEKEY` (vide = désactivé ; clé d'essai en local). Ordre : clé dans le code et push, PUIS activation dans Supabase (Attack Protection) avec la clé secrète.
  - Nouveaux mots de passe : 8 caractères minimum (inscription, réinitialisation) ; messages de Supabase traduits par `authErr`.
  - Sauvegarde automatique **en place depuis le 28/09/2026** : dépôt GitHub PRIVÉ `dexcraft-sauvegardes` (fichier `.github/workflows/sauvegarde.yml` = `outils/sauvegarde-auto.yml`, secrets `SUPABASE_DB_URL` et `SUPABASE_DB_PASSWORD`) : chaque nuit vers 4 h 30, gardée 30 jours (onglet Actions, « Artifacts ») ; GitHub prévient Theo par e-mail en cas d'échec. Sauvegarde à la main : `outils/sauvegarde.ps1` (pg_dump du schéma `public` et des comptes, dans `sauvegardes/`, 30 gardées ; restauration dans `sauvegardes/LISEZMOI.txt`). L'offre gratuite de Supabase n'en fait aucune.
- **Compatibilité des données** : un changement de format des annonces impose de vider le marché avec `delete from public.docs where coll = 'market';`. Ne jamais supprimer les lignes `coll = 'players'`.

## 7. Comment travailler sur ce dépôt

- Modifier `index.html` directement, en gardant le style du code existant : fonctions courtes, chaînes en français, pas de dépendance nouvelle.
- Après chaque modification, vérifier au minimum : ouverture d’un booster, collection, évolutions, échanges, profil.
- Commit en français, une phrase claire décrivant le changement. Le push sur `main` déclenche le déploiement sur Cloudflare Pages (dexcraft.fr) et GitHub Pages (ancienne adresse).
- **Version** : `APP_VERSION` dans `index.html`, affichée en bas à gauche. À **chaque push**, monter le dernier chiffre (0.2.1 → 0.2.2 → 0.2.3…), sauf si Theo dit explicitement qu'un ajout mineur ne change pas la version (alors ni version ni patchnote). Mise à jour majeure de la bêta : 0.3.0, puis nouveau cycle. Sortie publique : 1.0.0. Citer la version dans le message de commit.
- Ne pousser que sur signal explicite de Theo (« push »).
- **Patchnote** : à chaque push validé, donner à Theo un patchnote récapitulatif de la version, rédigé pour les joueurs.
- Toujours répondre à Theo en français.
- Prévenir les testeurs de recharger avec Ctrl + F5.
