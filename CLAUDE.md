# DexCraft — mémoire du projet

Ce fichier remplace l’historique des conversations. Toute session Claude Code doit le lire en premier (avec `CLAUDE.local.md`, notes privées non publiées), puis `index.html`.

## 1. Le projet en deux phrases

DexCraft est un jeu de collection de cartes Pokémon en français, inspiré de wiki-masters.com : on ouvre des boosters, on complète une collection et on échange entre joueurs (les enchères ont été retirées en 0.5.0). Sorti de bêta avec la 1.0.0 (version affichée en bas à gauche), sans limite de joueurs.

**Propriétaire du projet :** Theo (theo.lostria@gmail.com), administrateur du jeu.

## 2. Architecture

- **`index.html`** : tout le jeu, environ 4 900 lignes (500 Ko), souvent très longues (les données `DEX` et `EVO` tiennent chacune sur une seule ligne). HTML, CSS et JavaScript dans un seul fichier, sans dépendance à part `supabase-js` chargé depuis un CDN.
- **Hébergement (0.8.8)** : **https://dexcraft.fr**, domaine acheté chez OVH (renouvellement automatique), DNS gérés par Cloudflare (serveurs `denver` et `june.ns.cloudflare.com` ; e-mails : Cloudflare Email Routing, contact@dexcraft.fr renvoyé vers la boîte Gmail de Theo (réception seulement ; les MX OVH ont été supprimés, la boîte Zimbra d’OVH n’est pas active) ; DNSSEC actif depuis le 28/09/2026 : signé par Cloudflare (clé 2371, algorithme 13), enregistrement DS déclaré chez OVH, onglet « Enregistrements DS » ; l'interrupteur DNSSEC d'OVH reste désactivé. Pour l'arrêter un jour : retirer d'abord le DS chez OVH, attendre 24 h, puis désactiver chez Cloudflare, sinon le site devient injoignable). Site publié par **Cloudflare Pages** (projet `dexcraft`, relié au dépôt GitHub, branche `main` : chaque push redéploie). Commande de publication : `mkdir -p dist && cp -r index.html images favicon.svg favicon-32.png apple-touch-icon.png _headers robots.txt sitemap.xml dist/` (`robots.txt` et `sitemap.xml` depuis la 1.5.1, à ajouter par Theo dans Cloudflare), dossier publié `dist` : seuls ces fichiers sont en ligne (pas les scripts SQL, outils, notes). **Un nouveau fichier à mettre en ligne doit être ajouté à cette commande** (Cloudflare, Workers & Pages, dexcraft, Settings, Build). `www.dexcraft.fr` redirige vers `dexcraft.fr` (règle de redirection Cloudflare). L'ancienne adresse `letoucour.github.io/DexCraft` (GitHub Pages, toujours active tant que le dépôt est public) et `dexcraft.pages.dev` renvoient vers dexcraft.fr par un script en tête de page. Supabase, Authentication, URL Configuration : Site URL `https://dexcraft.fr`, Redirect URLs `https://dexcraft.fr/**`, `https://dexcraft.pages.dev/**` (et l'ancienne adresse). Vérifier un déploiement : `curl -s https://dexcraft.fr/ | grep APP_VERSION`.
- **Base de données** : Supabase (production `hxrbzhmzjeuhmaioqhdd`, test `thgyzfjozfhwefrztjfh`). Comptes e-mail et mot de passe. Table `docs` (`path`, `coll`, `data` jsonb, `updated_at`), table `admins`, table `game_config` (données du jeu pour le serveur), table `vb_rounds` (plateaux cachés de la VoltoBataille). **Offre Pro de Supabase depuis le 03/10/2026** (25 $ par mois, 10 $ de crédit de calcul inclus : machine Micro, 1 Go de mémoire, au lieu de Nano, 0,5 Go ; quotas bien plus larges : 250 Go de trafic, 5 millions de messages temps réel, 8 Go de disque ; sauvegarde quotidienne gardée 7 jours ; plafond de dépenses « Spend Cap » à laisser actif). Les économies de lecture décrites plus bas restent en place : ne pas les défaire.
- **Passer les SQL en une commande (1.6.3, demande de Theo : 11 fichiers à coller un par un pour la 1.6.3)** : `outilspasser-sql.ps1` (PowerShell, sur le PC de Theo) se connecte à la base de production avec `psql` (adresse de `sauvegardesdresse.txt`, mot de passe demandé une fois, jamais enregistré) et passe seulement les fichiers modifiés depuis le dernier passage, dans l'ordre ci-dessous (les trois parties de la configuration ensemble dès que l'une change, puis serveur 1 à 6, cartes secrètes, puis les migrations jamais passées, une seule fois chacune) ; chaque fichier d'un bloc (erreur : rien de ce fichier appliqué, arrêt, relancer reprend là). Mémoire des fichiers passés : `sauvegardessql-passes.txt` (état initialisé à la 1.6.3). Options `-Voir` (liste sans rien lancer), `-Tout`, `-Fichier`. Avec `psql`, la limite de 40 000 caractères de l'éditeur SQL ne s'applique plus, mais on garde le découpage (l'éditeur reste le secours). **Après une modification SQL, dire à Theo de lancer ce script, sans lui lister les fichiers.**
- **Scripts SQL, dans l'ordre** : `dexcraft-supabase.sql` (tables et droits) ; configuration en **deux fichiers** (l'éditeur SQL de Supabase tronque au-delà de ~40 000 caractères) : `dexcraft-config.sql` PUIS aussitôt `dexcraft-config-2.sql` et `dexcraft-config-3.sql` (données de l'Arène depuis la 1.3.0 : `arena`, `arStat`, `arChart`, `arBase`, clés `P3` de l'export) (évolutions `evo`, réserves de tirage `pool`, titres `titleDefs`… ajoutés à la partie 1 ; **incident de la 1.3.7** : la partie 1 lancée seule remplaçait toute la configuration, évolutions et titres ont cessé de marcher et les titres choisis des joueurs actifs ont été effacés par `dc__stamp` ; depuis, la partie 1 fusionne (`data || excluded.data`) et garde les clés des parties 2 et 3. Toujours donner les trois parties à Theo quand la config change), générés par `outils/generer-config.ps1` depuis `index.html?export-config` (clés de la partie 2 : liste `P2` de l'export) : à régénérer et relancer après tout changement de cartes, raretés, titres, boutique ou VoltoBataille ; puis `dexcraft-serveur.sql`, `dexcraft-serveur-2.sql`, `dexcraft-serveur-3.sql`, `dexcraft-serveur-4.sql`, `dexcraft-serveur-5.sql`, `dexcraft-serveur-6.sql`, `dexcraft-serveur-7.sql` (fonctions du jeu en cinq parties depuis la 1.3.0, la 5e pour l'Arène, la 6e pour le Souterrain depuis la 1.5.9, la 7e pour Lumi-Bois et la Pension depuis la 1.8.0 ; **chacune sous 40 000 caractères** : les compter avant de livrer ; chaque partie révoque elle-même les droits de ses fonctions) ; puis `secret/cartes-secretes.sql` (cartes secrètes, généré par `generer-config.ps1` sur le PC de Theo, jamais publié). **`migrations/`** : scripts passés une fois, par version. Ne jamais relancer `migration-1.0.0.sql` ; relançables sans risque (recalcul de tous les profils) : 0.8.9, 1.1.0, 1.1.7, 1.1.8, 1.1.14, 1.2.0 (qui corrige aussi la rareté des annonces), 1.3.6 (titre Invaincu rattrapé depuis la dernière partie de chaque joueur) ; `migration-1.3.7.sql` (rattrapage des récompenses du jour, à passer une fois AVANT `dexcraft-config.sql`, protégé par la marque `dailyRetro`) ; `migration-1.7.0.sql` (nouvelles raretés, relançable) ; `migration-1.6.3.sql` (2 Boosters Shiny dans la boîte cadeau des joueurs sans prestige, marque `giftShiny`, et retrait des annonces et propositions de cartes spéciales ; une fois, APRÈS les parties du serveur). Une nouvelle migration va dans ce dossier.
- **Chemins de données** : `players/<uuid>` pour un profil, `market/<id>` pour une annonce.
- **Le serveur est l'arbitre (depuis la 0.4.0)** : les joueurs ne peuvent QUE LIRE `docs`. Toute modification passe par une fonction SQL `dc_*` (`security definer`), appelée via `rpc(name, args)` dans `index.html`, qui renvoie le profil à jour. Hasard tiré côté serveur (`dc__rnd`, `gen_random_bytes`). Champs calculés par `dc__stamp` : `unique`, `byr`, `total`, `myth`, `trans`, `masterTs`, `beta`, `stats.maxCr`, `stats.days`. Les fonctions `dc__*` sont internes (non exécutables par les joueurs). Pour une nouvelle action : écrire une fonction `dc_*` qui vérifie tout, la tester sur PostgreSQL local, jamais d'écriture directe depuis le navigateur.
- **Tests** : sur ce PC (`localhost`, `127.0.0.1` ou fichier ouvert), `index.html` se branche automatiquement sur le projet Supabase de **test** (« BASE DE TEST » en bas à gauche). `outils/serveur-local.ps1` sert le jeu sur http://localhost:8123 et http://127.0.0.1:8123 (deux sessions, deux comptes). Comptes de test : `theo.lostria+test1@gmail.com` (admin) et `+test2`. PostgreSQL 17 est installé sur le PC pour tester le SQL hors ligne.
- **Codes cadeaux** (partie 3) : table `promo_codes` (`code` en majuscules, `credits`, `packs`, `active`, `max_uses` total ou null, et depuis la 1.2.6 `spec` : boosters spéciaux rangés dans l'inventaire, par exemple `'{"prem": 1}'` ou `'{"gen:3": 2, "type:10": 5}'`) et `promo_redemptions` (un code une fois par joueur). Section « Entrer un code » en bas du profil, fonction `dc_redeem_code`. Au plus 10 codes inconnus par heure et par joueur (`promo_tries`, 0.8.7 ; un code inconnu renvoie `{error}` au lieu d'une exception, pour que l'essai soit compté). Créer un code : `insert into public.promo_codes (code, credits, packs) values ('NOEL', 500, 5);` **dans l'éditeur SQL seulement, jamais dans un fichier du dépôt** (dépôt public). Désactiver : `update public.promo_codes set active = false where code = 'NOEL';`. Liste des codes existants : `CLAUDE.local.md` (privé).
- **Suppression d'un compte** (partie 3) : supprimer un utilisateur dans Supabase (Authentication, Users) supprime aussi son profil, sa manche de VoltoBataille et ses annonces (déclencheur `dc_user_deleted` sur `auth.users`, fonction `dc__purge_player`) : enchérisseurs remboursés, propositions rendues.
- **Couche de lecture (0.6.0, allégée en 0.8.4 pour le trafic de l'offre gratuite de Supabase, 5 Go par mois)** : on ne télécharge jamais les collections de tout le monde, seulement ce qui a changé, et rien quand l'onglet est caché (`document.hidden` ; au retour après plus de 30 s, tout est relu, `visibilitychange`). `loadPlayers` lit un résumé par joueur (`PL_FIELDS` : pseudo, image, titres affichés `shown`, compteurs du classement), chaque minute sur l'onglet Classement, toutes les 5 minutes ailleurs (`pollShared`). Son propre profil : temps réel filtré sur sa ligne (`dc-me`) ; chaque minute, `loadMe` lit seulement `data->updated` et ne relit le profil entier que s'il a changé (`onMine`, ignoré pendant une action `rpcBusy`). Marché : temps réel (`dc-market`) ; toutes les 2 minutes, `loadMarket` lit la liste légère (`path`, `updated_at`) puis seulement les annonces nouvelles ou modifiées (`MARKET_TS`) : toute modification d’une annonce côté serveur doit donc mettre à jour `updated_at`. **Depuis la 1.3.10 (trafic : 2,8 Go sur 5 en 5 jours, du 23 au 28/09/2026, avec 20 joueurs)**, la liste légère complète n’est relue qu’au démarrage, au retour après 5 minutes d’absence et toutes les 15 minutes (`marketFullTs`) ; entre-temps, seulement les annonces dont `updated_at` est postérieur à la dernière lue moins 2 minutes (`marketSince`) ; les annonces retirées arrivent par le temps réel, et celles touchées par sa propre action (`p_mid`, `p_mids`) sont vérifiées aussitôt. Collections des auteurs : toutes les 5 minutes, d’abord `data->updated` de chaque profil, la collection seulement si elle a changé (`OWNER_UPD`). **1.3.11** (journal des requêtes de Supabase : 1,26 Go en 5 jours, limite annoncée de 1 Go par mois, pas encore appliquée) : tant que le temps réel est connecté (`rtMe`, `rtMarket`, posés par le rappel de `subscribe`), les relectures de secours du profil et du marché passent à toutes les 5 minutes (`pollShared`) ; s’il décroche, retour au rythme d’avant (profil chaque minute, marché toutes les 2 minutes) ; à sa reconnexion, relecture immédiate pour rattraper la coupure. **1.3.12 : le marché n’est plus diffusé en temps réel à tous** (les messages temps réel croissaient en joueurs × changements : 204 000 en 5 jours à 20 joueurs, limite gratuite 2 millions par mois). Partie 4 du serveur : déclencheur `dc_market_trg` sur `docs` (les fonctions d’échange ne changent pas) qui note chaque annonce supprimée dans `market_gone` (gardée 2 jours) et, quand les propositions d’une annonce changent, prévient son propriétaire dans `pings` (une ligne par joueur, lisible par lui seul, suivie en temps réel par le canal `dc-ping`) ; `dc_market_since(p_since)` renvoie en une requête les annonces modifiées et supprimées depuis `p_since` (la page garde 2 minutes de marge, `marketSince` = heure du serveur moins 2 minutes). Page : `loadMarket` incrémental toutes les 2 minutes par `dc_market_since` (repli sur l’ancienne lecture si la fonction manque), liste complète toutes les 15 minutes ; un signal `dc-ping` ou un changement de son profil (`dc-me` : carte rendue ou reçue) relit le marché 0,7 s plus tard (`marketSoon`). Nouvelles annonces des autres : visibles en 2 minutes au plus (avant : aussitôt). **1.3.20 (charge du serveur : mémoire à 75 %, demande de Theo d’alléger)** : colonnes calculées par PostgreSQL à chaque écriture (`generated stored`, partie 4) : `upd` (date du profil) et `summary` (résumé du classement, `dc__summary`) ; `loadMe`, `loadPlayers` et `loadOwnerColls` les lisent au lieu de décompresser le profil entier (`LIGHT`, repli sur l’ancienne lecture si les colonnes manquent) ; index `docs_market_upd_idx` pour `dc_market_since`. **1.4.0 : la table `docs` quitte le temps réel** (Supabase, Query Performance : le décodage du journal des modifications pour le temps réel, requête `SELECT wal->>… as type`, prenait 44 % du temps du serveur, et la mémoire débordait sur le disque) : le déclencheur `dc_market_trg` allume aussi la ligne `pings` du joueur quand son profil change (`upd`), et la page, sur ce signal, relit la date du profil puis le profil entier s’il a changé (`meSoon`, regroupé) et le marché ; canal `dc-me` supprimé, seul `dc-ping` reste. Ne jamais remettre `docs` dans la publication `supabase_realtime`. **1.4.3 (serveur bloqué juste après le push de la 1.4.2, tous les joueurs rechargeant en même temps ; redémarré par Theo)** : `dc__stamp`, lancé à chaque action qui modifie un profil (et par `dc_init` à chaque connexion), recopiait à chaque carte la table des raretés (`dc__rar(cfg, …)`) et toute la collection déjà reconstruite (`newcoll || …`) : 250 ms pour un profil complet, 25 ms depuis (collection reconstruite en une requête, `rarm` lu une fois ; résultat vérifié identique sur la base locale). Premier chargement du marché en une passe par paquets de 1 000 (3 requêtes pour 2 700 annonces au lieu de 1 + 28). À garder en tête : machine gratuite de Supabase (0,5 Go de mémoire, swap élevé) ; l’offre Pro (25 $ par mois) inclut une machine deux fois plus grosse. Lectures longues paginées par 1 000 (`selectAll` : Supabase ne renvoie jamais plus de 1 000 lignes d'un coup). Collections des seuls auteurs d'annonces d'échange (`loadOwnerColls`, `OWNER_COLL`) : nouveaux auteurs tout de suite, toutes relues au plus toutes les 5 minutes. Profil complet d'un autre joueur seulement quand on l'ouvre (`loadPlayer`). Les titres affichés des autres joueurs viennent de `shown`, calculé par `dc__stamp` à partir de `cfg.titleDefs` (exporté par `titleDef` : un nouveau genre de titre doit être ajouté dans `titleDef` ET dans `dc__stamp`). Plus de partie locale : sans connexion, seul l'écran de connexion s'affiche.
- **Avertissements de Supabase (Security Advisor)** : « Signed-In Users Can Execute SECURITY DEFINER Function » est voulu (les `dc_*` sont l'interface du jeu ; chaque `dc_admin_*` vérifie l'administrateur). « Function Search Path Mutable » : corrigé en 0.8.4 par un bloc à la fin de chaque partie serveur, qui fixe `search_path = public, extensions` sur toute fonction `dc_*` qui n'en a pas. « Leaked Password Protection » : réservé à l'offre Pro, donc activable depuis le 03/10/2026 (Authentication, Attack Protection).
- **Historique des échanges** (partie 3) : table `trade_log`, écrite par `dc_trade_answer`, lisible seulement par les deux joueurs concernés (RLS). Bouton « Voir l'historique de mes échanges » dans l'onglet Échanges.
- **Récompense quotidienne** (partie 3) : `dc_daily_claim`, une fois par jour (heure de Paris), série de 7 jours `DAILY` dans `index.html` (exportée dans la config), qui repart à 1 si un jour est manqué. Depuis la 1.3.7 (demande de Theo) : boosters 10, 15, 20, 25, 30, 40, 50 (arrondis à 5, choix de Theo) et crédits 500, 700, 1 000, 1 400, 2 000, 2 800, 4 000 (×1,41 par jour) ; de la 1.0.3 à la 1.3.6 : boosters 1, 1, 2, 3, 5, 7, 10 et crédits 300 à 3 000 (×1,47 par jour) (pas de rattrapage des séries en cours : choix de Theo). Profil : `daily = {day, streak}`. Encadré « Récompense du jour » sur l'écran des boosters.
- **Mot de passe oublié** : lien sur l'écran de connexion (`resetPasswordForEmail`, retour sur la page avec `type=recovery`, formulaire `#gate-reset`, `updateUser`). Supabase, Authentication, URL Configuration : l'adresse du site doit être dans Site URL ou Redirect URLs.

### Shiny (1.1.0)

### Marché

- **Propositions de 12 h (1.7.0, demande de Theo)** : sans réponse au bout de 12 heures, une proposition expire et la carte revient à son auteur (`dc__expire_offers`, partie 6, lancée toutes les 10 minutes par pg_cron, tâche `dc-offres-12h`, programmée par la partie 6 ; la ligne de vérification de la partie 6 dit si pg_cron est actif) ; temps restant affiché (`offerLeft`, `OFFER_TTL`), message « Votre proposition … a expiré » au proposant. Recherche des annonces (1.7.0) : aussi par pseudo du joueur (`ownerMatches`).
- **Échanges** : le proposant met sa carte de côté, et c'est le propriétaire de l'annonce qui accepte ou refuse. Quatre types de demande : n'importe quelle carte de la rareté, n'importe laquelle **qui lui manque** (valeur par défaut), un Pokémon précis (`want`), ou **une liste de cartes précises** (1.0.3, `wantList` : 2 à 50 cartes du Pokédex de même rareté ; `dc__want_list` les filtre, une liste d'une seule carte devient `want`). Liste choisie dans le sélecteur `wantPickOpen` (recherche, « Seulement celles qui me manquent », bouton « 🔔 Ajouter mes cartes recherchées », silhouettes pour les cartes pas encore obtenues), depuis la fiche d'une carte (« Plusieurs cartes précises… »), la mise à l'échange groupée (`p_wants` de `dc_trade_create_many` : chaque annonce garde les cartes de sa rareté, celles sans aucune ne sont pas publiées, `nolist`) et « Mes annonces » (« Demander : une liste de cartes… », `dc_trade_bulk` mode `list`, annonces sans carte de leur rareté inchangées). `dc_trade_propose` refuse une carte hors de la liste ; côté page `canOffer` et `tradeWants`.
- **Dresseur d'origine (1.1.13, idée de Theo, contre les allers-retours qui gonflaient la chance de shiny)** : chaque exemplaire garde le dresseur qui l'a obtenu (booster, évolution, cadeau), même après plusieurs échanges, et ce dresseur ne peut JAMAIS le récupérer (circuit à trois compris). Profil : `ot = {n°: {uid: nombre}}` = exemplaires venus d'autres dresseurs, le reste est au nom du joueur (toutes les cartes d'avant la 1.1.13, sans migration). Annonce et proposition : champ `ot` de la carte mise en jeu ; on met en jeu d'abord un exemplaire à son nom (`dc__ot_take`, partie 2, qui évite aussi le destinataire connu) ; réception ou retour avec son origine (`dc__ot_give`) ; `dc_trade_propose` refuse une annonce dont on est le dresseur d'origine ; `dc__stamp` ne garde jamais plus d'exemplaires étrangers que d'exemplaires possédés (défausse et évolution consomment d'abord ceux à son nom). Anciennes annonces sans `ot` : au nom de leur propriétaire. Page : `otFrom`, `canOffer`, ligne « DO » (abréviation des jeux Pokémon, infobulle « Dresseur d’origine », choix de Theo) de l’annonce et de la fiche d’une carte (`otLine`), étiquette « Vient de vous » sur les tuiles.
- **Enchères : retirées en 0.5.0**, onglet, fenêtre de mise en vente, titres et textes compris. Ne pas les réintroduire sans demande de Theo.
- **Règle d'or du marché** : tout se règle côté serveur, de façon atomique (verrous de lignes). `dc_trade_propose` met la carte de côté, `dc_trade_answer` échange les cartes et rend celles des autres propositions, `dc_trade_cancel` rend tout. Le profil n'a plus de `listings` ni d'`escrow` : les annonces se lisent sur le marché.

## 5. Contraintes permanentes

- **Tout en français**, y compris les messages d'erreur et les commentaires de code.
- **Ne jamais dévoiler** l'existence des mythiques et des transcendantes dans un texte visible par un joueur qui n'en possède pas.
- **Illustrations** : `IMG_URL = "images/{id}.webp"` (chemin relatif, jamais de `/` au début : le jeu marche à n'importe quelle adresse), WebP 256 × 256 qualité 80 (`magick <png> -resize 256x256 -quality 80`, ou pour une image fournie : `-trim +repage -resize 240x240 -background none -gravity center -extent 256x256`) ; shiny dans `images/shiny/`, fiche d'appli dans `images/app/`. Surtout les illustrations officielles de PokeAPI ; exceptions fournies par Theo ou tirées de Pokémon HOME (voir « Cartes » et « Shiny »). Mythiques et transcendantes : images fournies par Theo, noms impossibles à deviner. PNG d'origine dans `images-png/`, `images-shiny-png/` et `images-perso/`, ignorés par git. Les illustrations appartiennent à Nintendo, Game Freak et The Pokémon Company : risque de demande de retrait, choix assumé par Theo.
- **Anti-triche** : depuis la 0.4.0, le navigateur n'a plus aucun droit d'écriture. Ne jamais réintroduire d'écriture directe dans `docs` depuis `index.html`, ni de calcul de hasard ou de gains côté navigateur : tout passe par `dc_*`.
- **Le dépôt est public** : ne jamais y écrire un code cadeau, le nom d'une carte secrète ou une donnée privée. Notes privées : `CLAUDE.local.md` (ignoré par git, à lire aussi). Dossiers ignorés : `secret/` (cartes secrètes), `sauvegardes/` (copies de la base : e-mails des joueurs).
- **Sécurité (0.8.7)** :
  - `supabase-js` chargé avec son empreinte (`integrity`, SRI) : à recalculer si on change de version (commande en commentaire au-dessus de la balise).
  - Balise `Content-Security-Policy` dans `<head>` : scripts seulement depuis le site, jsDelivr et Cloudflare (Turnstile), données seulement vers Supabase. Toute nouvelle ressource externe doit y être ajoutée. `_headers` : les mêmes règles plus l'interdiction d'afficher le jeu dans un cadre, pour Cloudflare Pages (ignoré par GitHub Pages).
  - 2 000 annonces d’échange ouvertes au plus par joueur (1 000 avant la 1.3.10, demande de Theo ; « Mes annonces » s’affiche par paquets de 120 avec « Afficher les suivantes », `myLimit`) (`dc__listing_cap`, `dc__open_listings`, partie 2 ; `dc_trade_create_many` publie jusqu'au plafond et renvoie `capped`).
  - Anti-robots Cloudflare Turnstile sur inscription, connexion et mot de passe oublié : `TURNSTILE_SITEKEY` (vide = désactivé ; clé d'essai en local). Ordre : clé dans le code et push, PUIS activation dans Supabase (Attack Protection) avec la clé secrète.
  - Nouveaux mots de passe : 8 caractères minimum (inscription, réinitialisation) ; messages de Supabase traduits par `authErr`.
  - Sauvegarde automatique **en place depuis le 28/09/2026** : dépôt GitHub PRIVÉ `dexcraft-sauvegardes` (fichier `.github/workflows/sauvegarde.yml` = `outils/sauvegarde-auto.yml`, secrets `SUPABASE_DB_URL` et `SUPABASE_DB_PASSWORD`) : chaque nuit vers 4 h 30, gardée 30 jours (onglet Actions, « Artifacts ») ; GitHub prévient Theo par e-mail en cas d'échec. Sauvegarde à la main : `outils/sauvegarde.ps1` (pg_dump du schéma `public` et des comptes, dans `sauvegardes/`, 30 gardées ; restauration dans `sauvegardes/LISEZMOI.txt`). L'offre gratuite de Supabase n'en fait aucune.
- **Compatibilité des données** : un changement de format des annonces impose de vider le marché avec `delete from public.docs where coll = 'market';`. Ne jamais supprimer les lignes `coll = 'players'`.

- Modifier `index.html` directement, en gardant le style du code existant : fonctions courtes, chaînes en français, pas de dépendance nouvelle.
- Après chaque modification, vérifier au minimum : ouverture d’un booster, collection, évolutions, échanges, profil.
- Commit en français, une phrase claire décrivant le changement. Le push sur `main` déclenche le déploiement sur Cloudflare Pages (dexcraft.fr) et GitHub Pages (ancienne adresse).
- **Version** : `APP_VERSION` dans `index.html`, affichée en bas à gauche. À **chaque push**, monter le dernier chiffre (0.2.1 → 0.2.2 → 0.2.3…), sauf si Theo dit explicitement qu'un ajout mineur ne change pas la version (alors ni version ni patchnote). Mise à jour majeure de la bêta : 0.3.0, puis nouveau cycle. Sortie publique : 1.0.0. Citer la version dans le message de commit.
- Ne pousser que sur signal explicite de Theo (« push »).
- **Patchnote** : à chaque push validé, donner à Theo un patchnote récapitulatif de la version, rédigé pour les joueurs.
- Toujours répondre à Theo en français.
- Prévenir les testeurs de recharger avec Ctrl + F5.
